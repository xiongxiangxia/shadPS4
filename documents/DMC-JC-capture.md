# JC jump-cancel melee capture

## Held charge across a play-mode change

The current candidate retains d7c3f399 buffer arbitration and adds a narrow correction to the actual-pawn PlayMode condition on an already-matched charge link. It applies only to an existing held-gun charge intent for the same player, gun event type Held, no active charge flag, a reflected requirement Normal=0, and current pawn mode Demon=1 or Angel=2. It changes the condition result, not the pawn mode, node state, input buttons, release or cleanup functions. A fresh grapple input made while a mode trigger is already held does not arm the compatibility intent. Other requirements and unknown/unreadable modes remain unchanged.

F9 may add COMPAT_CHARGE_MODE once per intent and at most 16 times per thread/capture, sharing the JC budget: record ID, condition object, matched link definition, pawn, compatibility gun enum (1 pistols/2 shotgun), required mode, actual pawn mode, original condition result, overridden result, intent generation, gun descriptor, event type. COMPAT_CHARGE_MODE_LIMIT means later overrides are unobserved. The record is emitted only when the original condition rejects and this correction applies; missing records do not prove a mode condition passed. Ordinary held_charge_mode=true milestones are bounded per intent. There is no new hook or repeated metadata walk.

## Current native input-buffer arbitration

The current candidate is based on the restored 8c8614fb playback behavior. It does not restore the forced Asleep/Awake route or manual link execution. One validated BufferEvent detour adjusts only competing pending inputs: new GunSpecial/LightMelee/StrongMelee Pressed may replace a queue containing solely the current gun's Held events through one original BufferEvent call, with its normal matching/conditions and ownership handling; the original strategy is restored before returning. Gun Held cannot overwrite a queue containing another descriptor or event type. Gun Released and mixed queues do not receive the attack-priority override. These changes require the same current player, gun intent, held input, no active charge flag, current synchronous event and matching intent generation. They do not alter action-node states, release/cleanup functions, projectiles or damage, and JC retry stays disabled.

F9 adds up to 64 COMPAT_BUFFER_DECISION records per thread/capture, sharing the JC budget. Repeated decision 1 for the same old owner is sampled at most every 50ms. COMPAT_BUFFER_LIMIT means later decisions are unobserved. F9 off skips the new snapshots; ordinary per-intent milestones remain bounded.

COMPAT_BUFFER_DECISION fields: record ID, decision (1 defer gun Held to preserve other queued input; 2 original attack-buffer admission with replacement enabled), native admission result (0 for decision 1), aggregate, incoming descriptor, incoming type, previous queue count, previous owner, queue count after the call/decision, owner after the call/decision, original strategy byte, restored strategy byte, current JC request if any. These are BufferEvent boundaries, not final aggregate boundaries, action execution, release completion, or damage confirmation. Event pointers are not retained; descriptor identity can appear in JC_OBJECT/JC_NAME. Unknown/unreadable layouts fall through without a compatibility decision.

## Restored playback foundation

The premature concurrent-charge experiments from d58a8b06/f6afb3f1 have been reverted after reports of missing shots/damage and lingering charge effects. The playback foundation is 8c8614fb, including the 2a33477b charge-intent behavior and the bounded GunSpecial observations below; the current candidate adds only the buffer arbitration described above. The experimental Asleep detour, manual link execution and COMPAT_CONCURRENT records are not installed. JC retry remains disabled. This remains a compatibility experiment, not a root-cause fix.

## Current GunSpecial investigation

The gameplay compatibility remains the 2a33477b behavior, including the safe live-copy performance change. This revision only adds F9 observations for DVButton_GunSpecial, kind 5 in JC_BEGIN. GunSpecial Pressed and Released events are traced; other recorded buttons remain Pressed-only, with the previous sparse JumpHeld observation. Aggregate acceptance is not proof of animation execution. Replayed GunSpecial events are captured through the existing graph handler and identified by their caller, without another hook or event query.

Format 6 adds bounded GS_STATE before/after the current player's GunSpecial aggregate, plus GS_NODE before/after graph handling. They report the current gun charge flag, physical input, mode, selected weapon, compatibility intent/retry count, buffered inputs, and active action/definition identities. All Token conditions encountered inside GunSpecial scopes may produce the existing JC_TOKEN_STATE counters/owners, not only MeleeDenied/EnemyStepDenied. The supported CUSA01022/01.03 NTPawn token-manager field +0x9c0 is checked against the NTTokenManager class. GunSpecial snapshots skip the old scan for DemonPull actions and timing configuration.

The existing PlayerTick observation may follow a GunSpecial aggregate for at most 400 ms, once per 50 ms at most. A newer GunSpecial replaces the watch. It validates the same player/aggregate and checks that the graph is still in the player's bounded graph array before reading it. It retains no pooled event pointers and calls no game operation. If this PlayerTick expression is not reached, follow-up rows may be absent; absence is not evidence that no action ran. Lifecycle records remain limited to calls made while a tracked event scope is active.

Limits per capture: 64 GS_STATE rows, 128 GS_NODE rows, 32 total token snapshots shared with older observations, 8 buffered events per state, at most 64 advertised buffered events, at most 32 graphs for follow-up validation. Limit markers are GS_STATE_LIMIT, GS_NODE_LIMIT, JC_STATE_LIMIT and the shared JC_LIMIT at 4096 records. No global animation or per-frame all-token scan is added. Cold class/field/name resolution and recording can still perturb timing; zero overhead is not claimed.

GS_STATE fields: request, phase (0 before / 1 after aggregate / 2 follow-up), aggregate, pawn, valid_mask, charge_float_bits, physical_buttons, game_mode, selected_weapon, compatibility_gun, retry_count, buffer_count, buffer_capacity, buffer_owner, buffer_policy, sampled_events, truncated, compatibility_milestones. Valid bits 1 charge, 2 buttons, 4 mode, 8 weapon, 16 buffer header, 32 complete sampled event-pointer array. A zero value without its valid bit is unknown. Milestones are the existing per-intent compatibility log flags, not game-state flags.

GS_BUFFER_ITEM fields: request, phase, index, event, readable, descriptor, combo, flags, event_type. Only the current safe snapshot is read; the event address is never saved for later use. GS_NODE fields: request, phase, graph, node, current_action, action_definition, state_readable, node_state, combo_window. Definition is read only for NTActionGraph_ActionNode instances. A selected link/definition does not prove a visible animation began.

GS_CONDITION pairs with JC_CONDITION by request and condition object: request, condition, readable, raw_config_word_0, raw_config_word_1. These are the condition's first 16 configuration bytes, not universal booleans or timings; interpret only after identifying the actual class and property layout. They allow checking requested mode/weapon/token polarity without a new reflection scan.

Report actual outcomes; no unmodified-game capture is required. Do not spam GunSpecial in the first comparison, since repeated inputs could hide a rejected first press.

## Previous bounded melee retry (disabled in this build)

Start with F9 off. After a Normal-mode Jump selects the specific Dante_DevilPull.Nodes.DemonPullJump link, a new Normal-mode LightMelee/StrongMelee press may be retained only if the player's aggregate rejects it and the Graph_MeleeRoot MeleeDenied condition was observed rejecting that same live event. The pending slot stores the button descriptor, never the pooled event pointer. The synchronous rejection observer is cleared before returning from the aggregate.

On the existing input-enabled PlayerTick path, use the controller's verified native SendActionGraphEvent implementation to construct a fresh Pressed event. All original melee conditions remain in force. Retry at most once per 16 ms, at most 12 attempts and no longer than 200 ms from rejection; the Leap eligibility itself expires after 400 ms. Stop at the first native acceptance (which may mean buffering, not animation execution). No global token override or Leap removal is added.

Require the same player/pawn/input context, the original Leap node still active in the current player's graph list, Normal mode, positive health and m_fcpInAir. A new Pressed command cancels the old pending slot; a newer eligible melee rejection can replace it. An accepted same-button Pressed/Held event also clears it. Releasing a short tap alone does not cancel an unaccepted press. Context changes, leaving Leap, landing, changing mode, death, expiry, or an unknown native sender discard it. A pause can prevent ticking; elapsed wall time then prevents stale replay on resume. No long-lived event object is retained and no input is inserted into unrelated gameplay states.

The possible visible side effect is a single delayed melee, at most 200 ms after the rejected press. This does not guarantee the same timing/route as a real PS4 JC. It deliberately does not carry the attack beyond Leap; if permission stays closed until Leap exits, it cancels instead of forcing an attack. Runtime performance and effectiveness are not yet verified.

Use dmc-jc-off.cmd to disable only this retry while keeping the working gun compatibility. dmc-compat-on.cmd enables both. SHADPS4_DMC_JC_COMPAT=0 is the independent environment switch; restart to apply. SHADPS4_DMC_COMPAT=0 still disables all compatibility. Ordinary shad_log.txt markers [DMC JC COMPAT] report enabled, retained, accepted, or cancelled; F9 is not required for initial play testing.

## Optional observation

Format 5 pairs each emitted JC_REEL_QUERY with JC_REEL_OUTPUT using the same request ID, without another hook or native query. The output snapshot follows the exact semantic-12/root-node lookup used by 0x9d0e70/0x2005af0, bounded to 32 attribute links and 32 event IDs. It records raw network update counters before/after the snapshot, output attribute frame, network phase, event count and IDs. The before/after bracket covers the output snapshot, not the original query. Concurrent updates or an incomplete bounded scan must not be treated as a consistent view.

JC_REEL_OUTPUT fields: request, action, network, valid_mask, update_before, update_after, node_id, phase, links_examined, attribute_entry, signed_attribute_frame, event_count, events_examined, requested_event_id, matching_ids, first_id_0..3, snapshot_us. Valid bits: 1 network update_before; 2 root-node lookup context; 4 matching semantic-12 attribute; 8 readable bounded event count; 16 all event IDs examined; 32 update_after; 64 owner/network identity checked and phase readable. Zero values without their validity bits have no diagnostic meaning. A frame value of -1 may be a persistent attribute; the lookup's -3 request bypasses frame comparison by design. A difference between update counter and attribute frame alone does not establish a stale read: phase/lifetime conventions still need validation.

Format 4 adds one optional verified native-exec observation at 0x20abfe0 for GetDiscreteEvent. The original executes first; results are never changed and the event query is not repeated. With F9 on, only the current player's DVAction_Dante_DemonPull_ReelIn.OnTick caller is observed, cross-checked against its m_Dante and m_MorphemeControl fields. A first sample, changed query result, or 50 ms since the previous sample emits a record, at most 64 per capture, with JC_REEL_LIMIT at exhaustion. Other native calls and F9-off calls simply forward. Installation failure is reported separately and does not disable the gun compatibility. JC melee retries remain unconditionally off.

The discrete event being requested is m_StartDeflectID (default 29; recorded from the actual pull parameters). ReelIn.OnTick uses a true result to stop the target reel, remove begin-denial tokens (including EnemyStepDenied), wake the node and send AutoContinue while still running. GetDiscreteEvent checks the animation controller and current sampled-event buffer; it does not remove an event when queried. A false result alone does not distinguish disabled controller, missing network/output, or absence of the event. Pointer/flag observations help identify some invalid-context cases, not all causes.

Record emission can still cause cold metadata overhead. JC_REEL_QUERY includes the instant the original query returned and the observation processing interval, so do not mistake the CSV row's later timestamp for the query instant. Runtime fields are read after the native returns, before the script caller continues; a true result does not by itself prove the later token deletion/wake completed.

Unchanged queries within 50 ms now bypass metadata validation only after a sample has validated the same action/controller/player tuple in this capture. Changed results, changed context and periodic samples still validate the player and controller fields before recording. Token snapshots and object identities share readable-region checks only within each synchronous observation, never across game execution. These reduce redundant memory checks, not cold reflection costs or all recording overhead; performance still needs runtime verification.

## Buffered Jump routing verified in the executable

SetState_Awake queues an operation for the original graph (0xa1ebf0, operation type 6), copying its buffered event references into the operation and clearing the source array. The operation dispatcher (0xa1f670, replay loop at 0xa1f8d0) calls the graph handler 0xa1fe10 for each event; it does not re-enter the global aggregate handler 0xa1f980. The queue processor 0xa1e830 drains its primary operations before deferred operations and guards against nested processing. This is game-native ordering, not evidence of a host scheduler race.

The ReelIn node is configured with NodeState_Buffer and NTAGBS_First. Its Jump link to DemonPullJump requires the Leap upgrade and DemonPullToPawn, but not Demon play mode. Releasing the trigger therefore does not invalidate that buffered route. The latest failed sample reached this link after the deflect event returned true; replay was not lost. The unresolved root-cause question is why the original Jump arrives while ReelIn still denies Enemy Step, rather than after the Deflect transition seen in a successful sample. Do not change global replay routing or remove denial tokens on this evidence alone.

## Record layout

All pointers are observations only; pooled event addresses are not identities across time. Nesting uses request/parent IDs, not event-pointer equality. Game results must be interpreted at their own layer: an aggregate/graph return value or selected link does not prove the attack animation executed.

- JC_CAPTURE: format version=4, budget=4096, name limit=128, compatibility active, identity limit=512, token snapshot limit=32, JC retry enabled (0 in this build), Reel query observer installed, Reel record limit=64. Version 3 added ownership/config snapshots. Version 2 introduced the filters described above; version 1 could exhaust its budget rapidly.
- JC_REEL_QUERY: independent record ID, action, Morpheme controller, configured event ID, original query result, original-return monotonic microseconds, field-valid mask, raw float bits of m_RunTime/m_fBufferTime/m_fReelDuration, consecutive query count for the cached action pointer, observation microseconds before final pointer/flag/name reads, controller flags byte, attached component pointer, cached animation network pointer. Valid bits 0..2 cover floats, bit 3 event ID, bit 4 flags. The action pointer may be reused across grapple attempts; its query count is not a unique action-lifetime identifier. JC_OBJECT carries its identity when budget permits.
- JC_REEL_LIMIT: the 64 Reel-query-record limit was reached. Missing later records cannot establish that the animation event never arrived.
- JC_TOKEN_STATE: active request, condition, pawn, token manager, token FName, status (1 matched, 2 absent, 3 unreadable/type mismatch, 4 invalid layout, 5 collision chain limit), counter, owner count, sampled owners, flags (bit 0 owners truncated, bit 1 owner array unreadable), collision steps, eight owner FNames. A match with counter 0 differs from a missing map entry. The condition result remains in JC_CONDITION.
- JC_ACTION_CLOCK: active request, graph, active node, action, runtime readable, raw float bits of m_RunTime, timeline, timeline clock readable, raw float bits of timeline time. Exact action identity/class is in JC_OBJECT. Only the three named Demon Pull action classes are included, so absence is not proof that the player has no other active action.
- JC_ACTION_CONFIG: active request, action, definition, valid field mask, AnimationLength float bits, IntoAnimationLength float bits, SettleAnimationLength float bits, PlaySpeed float bits, LoopCount integer, raw float bits at definition+0x160. Bits 0..5 of the valid mask correspond to those six values. The last value is read only for NTActionDef_Attack subclasses and is the denominator used by the verified ToAbsoluteTime native helper, not an independently identified property name. The first five values use reflected property offsets. This is a read-only sample, not a native function invocation; it does not itself capture every subclass override of GetTimelineLength. Correlate raw values with the correct definition's code before calculating a deadline. Config snapshots share the same two-action/32-snapshot limits as action clocks.
- JC_STATE_LIMIT: the independent 32-token-snapshot limit has been reached. It does not imply that all other JC records have stopped.
- JC_BEGIN p0=request, p1=parent, p2=stage (0 graph, 1 aggregate, 2 selector), p3=owner, p4=event, p5=kind (1 Jump, 2 LightMelee, 3 StrongMelee, 4 RangedAttack), p6=raw event type, p7=combo, p8=flags, p9=event play mode, p10=held input mask, p11=NTInput current mask, p12=mask readable, p13=NTInput pointer, p14=caller RVA. Modes: Normal=0, Demon=1, Angel=2. Do not confuse NTInput bit positions with the scePad mask.
- JC_END: request, stage, result (selector uses the returned link pointer).
- JC_ACTIVE: request, before=0/after=1, graph, active node. Only synchronous graph-call boundaries are observed, not all future node changes.
- JC_HELD_GRAPH: graph, active node before, active node after, result. Jump-Held only; emitted for first accepted result, changes relative to the graph's previous result/after-node pair, or a node change during this call. Repeated unchanged results are omitted. No parent request or condition expansion is implied.
- JC_MATCH: active request, candidate definition, native match result. This is before link conditions, not final acceptance.
- JC_CONDITION: active request, caller RVA, condition object, function, context, pawn, original result. Captures verified graph/selector/link condition sites only. For gun events this precedes any compatibility override; jump and melee conditions are not rewritten.
- JC_TOKEN: active request, condition, raw token FName. Only emitted for token-condition class.
- JC_LIFECYCLE: active request, object, function, caller RVA. Limited to the already-identified immediate action-lifecycle dispatch range. Absence does not prove no later/asynchronous action callback occurred.
- JC_OBJECT: active request, object, full FName, class, full class FName. Low 32 bits of an FName are its name index; high bits are the instance suffix.
- JC_NAME: index, wide flag, sixteen little-endian 64-bit payload words (128 bytes, null-terminated if the name fits). Names longer than this payload are truncated. The data is copied while the game objects are live; no event pointer is retained for later use.

The first capture should locate the first divergence: mapped input to scePad delivery, delivery to game event creation, or event creation to a rejected/accepted transition. If a selected melee later disappears, a further tightly scoped lifecycle/buffer observation may be necessary. These records do not by themselves prove an emulator defect or reproduce PS4 hardware behavior.
